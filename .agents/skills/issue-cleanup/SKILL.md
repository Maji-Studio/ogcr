# Issue Cleanup

Groom the open backlog in five phases: scan → multi-agent verdicts → approval → execute → grill.
Verify claims against current code. No GitHub write happens before the maintainer approves the batch.

Paths are relative to the repository root. Prerequisites: authenticated `gh` and Node.js.

## Phase 0 — Scan

```bash
node .claude/skills/issue-cleanup/scan-issues.mjs <scratchpad-dir>/issue-cleanup
```

This writes `issues-snapshot.json` (all open issues with bodies, comments, closing-PR refs,
sub-issue relations; recently-closed issues for dedup; recent merged PRs) and `issues-index.md`
(one line per issue). **Never `Read` the whole snapshot** — it can run to hundreds of KB.
Extract only the issue numbers being reviewed:

```bash
node -e 'const s=require("<abs-path>/issues-snapshot.json");const want=new Set([25,33]);console.log(JSON.stringify(s.openIssues.filter(i=>want.has(i.number)),null,1))'
```

Also read `CLAUDE.md`, `PLAN.md`, relevant package docs, `docs/adr/` when present, and
`packages/design-system/docs/design-system.md` for design-system issues.

## Phase 1 — Verdicts

Run `.claude/workflows/issue-cleanup-verdicts.js` via the Workflow tool (this skill's invocation
is the user's opt-in to orchestration):

```
Workflow({
  scriptPath: ".claude/workflows/issue-cleanup-verdicts.js",
  args: { snapshotPath: "<abs>/issues-snapshot.json", indexPath: "<abs>/issues-index.md" }
})
```

Pass `args.clusters: [{ key, issues: [numbers] }]` to scope a run to a subset (also how you
re-run `failedClusters` from a previous result). Absolute paths only — subagents don't share
your cwd assumptions.

The script clusters the backlog, verifies each issue against code, and asks an independent
skeptic to challenge every destructive verdict (`close-*`/`merge`). Failed skeptic or cluster
runs fail safe to `keep`.

Verdict vocabulary:

| Verdict | Meaning | Carries |
|---|---|---|
| `close-implemented` | behavior already exists | file:line + PR/commit evidence |
| `close-obsolete` | superseded by ADR/redesign/newer issue | superseding ref |
| `merge` | duplicate of an older open issue | `mergeInto` (canonical = oldest) |
| `split` | too big for one PR | `proposedSlices` (vertical slices) |
| `enhance` | keep, body stale vs. code | `staleNotes` |
| `grill` | keep, under-specified | `openQuestions` |
| `stakeholder-question` | needs an external answer before work | `stakeholderQuestion` {question, audience, blocks, options} |
| `keep` | already clear | — |

Decisions that depend on policy, product direction, upstream design-system ownership, or
stakeholder intent stay open until authoritative evidence is available.

The result also aggregates `stakeholderQuestions` (from any verdict, not just
`stakeholder-question`), `downgradedBySkeptic`, and `failedClusters` (re-run these — they are
NOT covered).

## Phase 2 — Approval

Present one table grouped by verdict: issue · age · labels · verdict · evidence · proposed action.
Use AskUserQuestion for genuinely contested rows; plain review for the rest. The maintainer
approves or amends each destructive action. Write stakeholder questions to
`<scratchpad>/issue-cleanup/stakeholder-questions.md` (per issue: decision-ready question,
audience, what it blocks, options) so the pack can be shared as-is.

## Phase 3 — Execute approved rows

Every automated triage comment begins:

```text
> *This was generated by AI during triage.*
```

- **Close (implemented / obsolete)** — only with concrete code, commit, PR, ADR, or product
  evidence. Evidence comment first, then close:
  ```bash
  gh issue comment <n> --body-file <comment.md>
  gh issue close <n> --reason completed        # implemented
  gh issue close <n> --reason "not planned"    # obsolete
  ```
- **Merge** — rewrite the canonical (oldest) issue's body to absorb the dupes' unique
  requirements (`gh issue edit <canonical> --body-file <new-body.md>`), then close each dupe:
  ```bash
  gh issue close <dupe> --duplicate-of <canonical> --comment "<disclaimer> Consolidated into #<canonical>."
  ```
- **Split** — create sub-issues as tracer-bullet vertical slices (the `to-issues` template:
  What to build / Acceptance criteria / Blocked by), then attach natively and rewrite the
  parent as an epic overview:
  ```bash
  gh issue create --title "<type>: <slice>" --body-file <slice.md> --label <labels>
  gh issue view <n> --json id --jq .id     # node IDs for parent + child
  gh api graphql -f query='mutation($p:ID!,$c:ID!){ addSubIssue(input:{issueId:$p, subIssueId:$c}){ subIssue { number } } }' -f p=<parentId> -f c=<childId>
  gh issue edit <parent> --body-file <epic-overview.md>
  ```
- **Enhance** — `gh issue edit <n> --body-file <refreshed.md>`; normalize labels with
  `--add-label`/`--remove-label`, only to labels already present in the repository.
- Do not edit ProjectV2 board fields unless the user separately requests it.

Use discrete `gh` commands and stop on errors. Never chain write operations.

## Phase 4 — Grill

Rank under-specified survivors by value and use `grill-with-docs` to resolve terminology and design
decisions. Refresh issue bodies after decisions land and record pending issue numbers for resumption.

## Phase 5 — Report

Return issue links grouped by closed, merged, split, enhanced, pending-grill, and stakeholder question,
plus any clusters that failed and remain uncovered.

## Gotchas

- **Workflow args may arrive as a JSON string** depending on the caller — the script tolerates
  both. Symptom of passing stringified args elsewhere: `args.snapshotPath` undefined at line 1.
- **Skeptic fail-safe:** a destructive verdict whose skeptic agent dies is downgraded to
  `keep`, not trusted. Same for `failedClusters` — absent ≠ clean.
- **`--reason` takes `"not planned"` with a space** (quote it); `completed`, `not planned`,
  `duplicate` are the only values. `--duplicate-of` implies the duplicate reason.
- **Never mutate `agent()`/`parallel()` results in place** inside the workflow script — values
  crossing the runner's sandbox boundary are cloned (and may be frozen), so in-place edits
  vanish silently. Rebuild objects functionally (`{ ...v, verdict: … }`).
- **Linters flag top-level `return`/`await` in `.claude/workflows/*.js`** as parse errors —
  false positive; that's the Workflow-runner contract. Reject such review findings.
- The snapshot is point-in-time; rescan after issue changes.
